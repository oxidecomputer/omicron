= JBOR Quickstart: 2-Rack BGP Peering

This guide walks through launching a 2-rack, 2-external-peer-router
topology with `jbor` and configuring BGP peering on rack 0 via the
`oxide` CLI.

For topology details and other options, see the link:README.md[jbor README].

== Prerequisites

* Helios host with elevated privileges (`pfexec` / root)
* omicron workspace built: `cargo build -p jbor`
* `oxide` CLI installed: https://github.com/oxidecomputer/oxide.rs
* `jq` installed (used to extract values from `jbor.json`)
* omicron development environment active (`source env.sh`; provides `mgadm`)

== Optional

This document can be executed and validated with `mighty-docs`. If you want this
quickstart topology in a single command, install [`mighty-docs`][1], launch the
topology, then run `mighty-docs dev-tools/jbor/quickstart.adoc`.

== Launch the Topology

In a dedicated terminal, launch two racks with two external peer routers:

[source,sh]
----
pfexec ./target/debug/jbor --count 2 --peer-routers 2
----

jbor prints startup information as services come up. Once all services are
ready it writes `jbor.json` (in the current directory by default; override
with `--state PATH`) and then waits for Ctrl-C. Leave jbor running in this
terminal and open a second terminal for the remaining steps.

Expected output includes:

[source]
----
peer router 0: mgd api:                http://[::1]:<port>
peer router 0: mgd bgp-dispatcher:     tcp 100.64.0.1:179
peer router 0: bgp ASN:                65100

peer router 1: mgd api:                http://[::1]:<port>
peer router 1: mgd bgp-dispatcher:     tcp 100.64.0.2:179
peer router 1: bgp ASN:                65101

rack 0: setting up all services...
rack 0: services are running.
rack 0: nexus external API:     0.0.0.0:<nexus-port>
rack 0: mgd bgp-dispatcher:     tcp 100.64.1.0:1049 (Switch0)
rack 0: mgd bgp-dispatcher:     tcp 100.64.1.1:1049 (Switch1)
rack 0: silo name:              <silo-name>
rack 0: privileged user name:   <username>
rack 0: privileged password:    <password>

rack 1: setting up all services...
...
----

NOTE: The peer routers (`100.64.0.x`) and the rack switches (`100.64.1.x`)
are all assigned to the loopback interface (`lo0`). BGP sessions between
them are established over loopback.

== Authenticate with the oxide CLI

Once jbor has written `jbor.json`, read the Nexus host and bearer token
for rack 0 from it and verify connectivity:

[source,sh,doctest=command]
----
OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
oxide system hardware rack list | jq -r '.[0].id'
----

[source,doctest=response]
----
..........<REDACTED_UUID>...........
----

== Configure BGP on Rack 0

The following steps configure BGP on switch0 of rack 0, peering with both
external peer routers (`100.64.0.1` and `100.64.0.2`) launched by jbor.

=== Create a Peering Address Lot

The Oxide platform requires addresses to be allocated from named _address
lots_. Create a lot for the IP address we'll assign to switch0's uplink
port for BGP peering. The peer routers are on `100.64.0.0/24`, so we use
an address from that subnet:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
cat > /tmp/peering-lot.json <<'EOF'
{
  "name": "peering",
  "description": "addresses for bgp peering",
  "kind": "infra",
  "blocks": [
    {"first_address": "100.64.0.10", "last_address": "100.64.0.11"}
  ]
}
EOF
oxide system networking address-lot create \
  --name peering \
  --description 'addresses for bgp peering' \
  --json-body /tmp/peering-lot.json
----

[source,json,doctest=response]
----
{
  "blocks": [
    {
      "first_address": "100.64.0.10",
      "id": "..........<REDACTED_UUID>...........",
      "last_address": "100.64.0.11"
    }
  ],
  "lot": {
    "description": "addresses for bgp peering",
    "id": "..........<REDACTED_UUID>...........",
    "kind": "infra",
    "name": "peering",
    "time_created": "<REDACTED_TIMESTAMP>",
    "time_modified": "<REDACTED_TIMESTAMP>"
  }
}
----

=== Create a BGP Announce Set

Create an _announce set_ containing the prefixes rack 0 will advertise to
its peers. Announce set entries are tied to address lots; first create a lot
to hold the prefixes to announce, then create the announce set referencing it.

We use `198.51.100.0/24` (TEST-NET-2, RFC 5737) as a placeholder prefix:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
cat > /tmp/instances-lot.json <<'EOF'
{
  "name": "rack0-instances",
  "description": "instance prefixes for rack 0",
  "kind": "pool",
  "blocks": [
    {"first_address": "198.51.100.0", "last_address": "198.51.100.255"}
  ]
}
EOF
oxide system networking address-lot create \
  --name rack0-instances \
  --description 'instance prefixes for rack 0' \
  --json-body /tmp/instances-lot.json
----

[source,json,doctest=response]
----
{
  "blocks": [
    {
      "first_address": "198.51.100.0",
      "id": "..........<REDACTED_UUID>...........",
      "last_address": "198.51.100.255"
    }
  ],
  "lot": {
    "description": "instance prefixes for rack 0",
    "id": "..........<REDACTED_UUID>...........",
    "kind": "pool",
    "name": "rack0-instances",
    "time_created": "<REDACTED_TIMESTAMP>",
    "time_modified": "<REDACTED_TIMESTAMP>"
  }
}
----

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
cat > /tmp/announce-set.json <<'EOF'
{
  "name": "rack0-prefixes",
  "description": "prefixes to announce from rack 0",
  "announcement": [
    {
      "address_lot_block": "rack0-instances",
      "network": "198.51.100.0/24"
    }
  ]
}
EOF
oxide system networking bgp announce-set update \
  --name rack0-prefixes \
  --description 'prefixes to announce from rack 0' \
  --json-body /tmp/announce-set.json
----

[source,json,doctest=response]
----
{
  "description": "prefixes to announce from rack 0",
  "id": "..........<REDACTED_UUID>...........",
  "name": "rack0-prefixes",
  "time_created": "<REDACTED_TIMESTAMP>",
  "time_modified": "<REDACTED_TIMESTAMP>"
}
----

=== Create a BGP Configuration

Create a BGP configuration for rack 0. We use ASN 65000 for the rack; the
peer routers launched by jbor use ASNs 65100 and 65101, so the sessions
will be eBGP:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
oxide system networking bgp config create \
  --name rack0-bgp \
  --description 'rack 0 bgp configuration' \
  --asn 65000 \
  --bgp-announce-set-id rack0-prefixes
----

[source,json,doctest=response]
----
{
  "asn": 65000,
  "description": "rack 0 bgp configuration",
  "id": "..........<REDACTED_UUID>...........",
  "max_paths": 1,
  "name": "rack0-bgp",
  "time_created": "<REDACTED_TIMESTAMP>",
  "time_modified": "<REDACTED_TIMESTAMP>"
}
----

=== Add a Peering Address to Switch0

Assign address `100.64.0.10/24` from the `peering` lot to switch0's uplink
port. This address is on the same subnet as the peer routers and serves as
the source address for BGP sessions:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
RACK_ID=$(oxide system hardware rack list | jq -r '.[0].id')
oxide system networking addr add \
  --rack $RACK_ID \
  --switch switch0 \
  --port qsfp0 \
  --addr 100.64.0.10/24 \
  --lot peering
----

[source,sh,doctest=response]
----
----

=== Configure BGP Peers on Switch0

Add both peer routers as BGP peers on switch0. Run the command once for
each peer router:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
RACK_ID=$(oxide system hardware rack list | jq -r '.[0].id')
oxide system networking bgp peer set \
  --rack $RACK_ID \
  --switch switch0 \
  --port qsfp0 \
  --addr 100.64.0.1 \
  --bgp-config rack0-bgp \
  --hold-time 6 \
  --idle-hold-time 6 \
  --delay-open 0 \
  --connect-retry 3 \
  --keepalive 2
----

[source,sh,doctest=response]
----
----

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
RACK_ID=$(oxide system hardware rack list | jq -r '.[0].id')
oxide system networking bgp peer set \
  --rack $RACK_ID \
  --switch switch0 \
  --port qsfp0 \
  --addr 100.64.0.2 \
  --bgp-config rack0-bgp \
  --hold-time 6 \
  --idle-hold-time 6 \
  --delay-open 0 \
  --connect-retry 3 \
  --keepalive 2
----

[source,sh,doctest=response]
----

== Configure BGP Neighbors on Peer Routers

Each peer router needs a neighbor entry pointing to the rack switch it will
peer with. Read the peer router admin ports from `jbor.json` and add a
neighbor for switch0 of rack 0:

[source,sh,doctest=command]
----
PR0_PORT=$(jq -r '.peer_routers[0].mgd_port' jbor.json)
mgadm -p $PR0_PORT bgp config neighbor create \
  rack0-switch0 100.64.1.0 default 65100 \
  --port 1049 \
  --src-addr 100.64.0.1 \
  --enable-ipv4
----

[source,sh,doctest=response]
----
----

[source,sh,doctest=command]
----
PR1_PORT=$(jq -r '.peer_routers[1].mgd_port' jbor.json)
mgadm -p $PR1_PORT bgp config neighbor create \
  rack0-switch0 100.64.1.0 default 65101 \
  --port 1049 \
  --src-addr 100.64.0.2 \
  --enable-ipv4
----

[source,sh,doctest=response]
----
----

== Verify BGP Sessions

Check that both peer sessions have reached the established state. It may
take a few seconds after the peer configuration is applied:

[source,sh,doctest=command]
----
export OXIDE_HOST=$(jq -r '.racks[0].nexus_host' jbor.json)
export OXIDE_TOKEN=$(jq -r '.racks[0].oxide_token' jbor.json)
oxide system networking bgp status | sed '/duration/d' | jq 'sort_by(.addr)'
----

[source,json,doctest=response]
----
[
  {
    "addr": "100.64.0.1",
    "local_asn": 65000,
    "peer_id": "100.64.0.1",
    "remote_asn": 65100,
    "state": "established",
    "switch": "switch0"
  },
  {
    "addr": "100.64.0.2",
    "local_asn": 65000,
    "peer_id": "100.64.0.2",
    "remote_asn": 65101,
    "state": "established",
    "switch": "switch0"
  }
]
----
(note for mighty-docs users: this output does not come sorted from the API,
so we sort it with jq for now to stabilize the output)

Both sessions show `established`, confirming the rack is exchanging routes with
both peer routers. The command filtered `duration` from the output to make
it a stable comparison for `mighty-docs`.

To apply the same configuration to rack 1, repeat the steps above against
rack 1's Nexus URL using ASN `65001` and addresses `100.64.2.0:1049`
(switch0) / `100.64.2.1:1049` (switch1).

== Tear Down

Press *Ctrl-C* in the jbor terminal. jbor cleans up all processes,
temporary files, and loopback IP allocations before exiting.
